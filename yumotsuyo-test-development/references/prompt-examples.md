# 使用例

## 作成モード

```text
$yumotsuyo-test-development を使い、添付した仕様書をテストベースとして、ボリュームコントロール機能のシステムテストを設計してください。

対象：VOL操作受付、動作状態による対象系統選択、音量step変換、上下限維持、設定値保持
目的：仕様適合性の確認と、状態・操作順序・設定値反映の不整合リスクの確認

TRAからTIまで順番に作成し、不明点は推測せず「要確認」としてください。
```

## レビューモード

```text
$yumotsuyo-test-development のレビューモードで、仕様書と既存のテスト設計書を比較してください。

提出物だけを読んでコメントするのではなく、仕様書から独立にTRA・TAD・TDDの分析を行ってから比較してください。仕様理解、リスク、論理的機能構造、P-V、期待結果、トレーサビリティの観点で、重大度と根拠を示してください。ファイルは変更しないでください。
```

## 工程を限定する例

```text
$yumotsuyo-test-development を使い、まずTRAだけを実施してください。仕様書から振る舞い断片を抽出し、Mermaid対象理解モデル、機能・仕様紐付け、機能一覧、品質リスク、テスト条件候補、不明点を提示してください。未割当・重複を確認して機能一覧をブラッシュアップし、TADにはまだ進まないでください。
```

## TIの粒度例

P-Vの水準は論理テストケースとして保持し、同じ前提、操作、確認箇所を共有する場合は1本のプロシジャー内の反復テストデータにする。

正例：

```text
TP-01 人数入力境界
共通操作：値を入力してフォーカスアウトし、項目エラーと計算ボタン状態を確認する。
反復テストデータ：
- TC-01 空 → 必須エラー、計算不可
- TC-02 0 → 範囲エラー、計算不可
- TC-03 1 → 有効
- TC-04 99 → 有効
- TC-05 100 → 範囲エラー、計算不可
- TC-06 非数値 → 形式エラー、計算不可
```

反例：値だけが異なる`空、0、1、99、100、非数値`を、それぞれ別のテストプロシジャーへする。

業務シナリオでは、前の事後状態を次の前提として使える場合に、`登録 → ログイン → 検索 → 購入 → 履歴確認 → キャンセル`のように実行しやすい順へ並べる。前の失敗で後続判定が不能になる場合や、異常終了が共有データを壊す場合は分離する。
